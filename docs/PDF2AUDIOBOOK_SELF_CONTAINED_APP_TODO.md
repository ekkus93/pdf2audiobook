## Working rules

- Work in the order below. Task 1 decides whether C2 holds; record its measurements before building on it.
- Write each task's tests first and run them against the parent commit, so the failing test IDs are recorded before the fix.
- Use `[x]` only when the implementation exists and its named tests pass. Otherwise mark the item partial in the ledger.
- Conventional Commits (`build`, `desktop`, `ci`, `docs` scopes as they fit), lowercase imperative subject, no body.
- Before each commit: `/verify` for Python changes; for `desktop/` changes, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `npm run lint`, `npm run typecheck` and `npm test`, checking each command's exit status, not only its counts.
- Check Desktop CI and Python CI after every push. A failed run blocks the next task until it is fixed or explained.
- CI stays offline except package installs and the explicitly pinned downloads the build fetches. Never commit model weights, binaries, generated audio or private paths.

## Unresolved limitations

Recorded by 9.2 on 2026-11-27. SC1, SC2 and SC4–SC8 are met with tests and CI evidence; SC3 is met except its manual real-network run.

1. **Manual real-network add-on run (4.5, SC3).** Installing both add-ons over the network, cloning a voice and running an audio check needs a reference recording; it would also be the first real exercise of add-on progress and Stop, which tests cover with small local packages and a stand-in pip.
2. **A person converting a book through the app on a clean desktop (9.1).** Automated evidence covers the parts separately: the CI-built `.deb` installed on stock Ubuntu 22.04 pulls in no Python, FFmpeg, Tesseract or espeak, and with no network the installed app starts and its engine converts the demo book; the CI-built AppImage starts offline on stock Ubuntu with only a virtual display and the standard desktop libraries added; and Desktop CI's walkthrough converts through the app with only its built-in engine. The remaining step is running the CI AppImage or `.deb` on a desktop and converting a book from the window.
3. **Add-on progress is per package and per file.** The largest single downloads (the CPU PyTorch wheel, the 1.6 GB Kitten 2 model, the 1.5 GB Whisper model) each count as one step, so the bar can sit still for minutes.
4. **The installers are AGPL-3.0 as a whole (owner decision, 2026-11-27).** The code stays Apache-2.0; PyMuPDF (AGPL-3.0) and the GPL components make the distributed app an AGPL-3.0 work. About says so and lists the app's own crates and npm packages as well as the engine's components, and Desktop CI uploads the source archive with the installers. There is no release process yet: whoever publishes an installer must publish its source archive with it. This is the standard reading of the licences, not legal advice.
5. **Platform.** Linux x86-64 with glibc 2.35 or newer (Ubuntu 22.04 and later), unsigned. The AppImage relies on the desktop's own Wayland, EGL/GLES, HarfBuzz and FriBidi libraries, which linuxdeploy leaves out on purpose; every desktop install has them, a bare server does not. Installers built on a newer distribution need that distribution's glibc, so released installers must come from Desktop CI.
6. **Add-ons are per app version.** After each update they must be installed again (about 3.2 GB each), as SC3 chose for safety.
7. **The build depends on upstream downloads.** A cold engine cache downloads the pinned sources from ffmpeg.org, SourceForge (LAME), GitHub (Python, tessdata, licence texts) and Hugging Face (the voice model). Each is checked by hash, so a changed file fails the build rather than slipping in, but a removed one stops it until it is re-pinned.
8. **espeak-ng's 160-byte data path.** An engine under a long folder gets a temporary symbolic link to the voice data (`tts/espeak_path.py`); the clean-machine check covers it.
